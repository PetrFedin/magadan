# ГИДРОКОНТУР 360 — МАГАДАН / V7

**Дата:** 20.10.2026. **Статус:** локальная исследовательская серверная лаборатория, **PRODUCTION HOLD**.

## Отличия от V6

V6 — автономная клиентская демонстрация шести направлений. V7 дополняет её **отдельным** FastAPI-сервером для серверной авторизации, разграничения организаций, подтверждённых версий расчётных источников, модели AC двухузловой сети, аудируемого цикла решения. Код V6 сохранён в `v6-client/`, но его шесть старых клиентских модулей **НЕ подключены к серверу V7** — они продолжают работать только как автономная демонстрация. Новый серверный UI — `server/ui/`.

**Не делалось:** изменения GitHub-репозитория, внешняя публикация приложения, производственные подключения, промышленная верификация, использование данных ПАО «РусГидро», «Колымаэнерго», «Магаданэнерго» или муниципальных объектов.

## Возможности V7, проверенные локально

1. Argon2id + JWT со сроком действия 15 минут; вход/выход, активное membership на каждом API-запросе.
2. Разрешённый контекст организации берётся из базы, роль из JWT или HTML не принимается.
3. Источники и версии модели хешируются SHA-256 и проверяются независимым пользователем (lab auditor).
4. Расчёт `balanced_two_bus_AC_PQ_lab_v1` выполняет численное решение нелинейных узловых уравнений и сравнивает его с аналитическим решением для высоковольтной ветви двухузловой сети.
5. Создаётся инициатива только на базе сохранённого расчёта. Документы инженерного, финансового, руководящего и итогового сопровождения имеют отдельные схемы, хеши и привязку к номеру расчёта.
6. Семь серверных переходов от draft до verified с проверкой полномочий, документов, ревизии и разделения ролей. Состояние в интерфейсе нельзя подменить произвольным запросом.
7. Аудит HMAC с последовательностью, хеш-связью и обнаружением вмешательства; локальные SQLite-триггеры запрещают штатное изменение/удаление записей.
8. Адаптивный веб-интерфейс `/lab` без изменения роли из UI; сервер OpenAPI `/openapi.json`.
9. Серверная финансовая функция DCF на структурированном SYNTHETIC-документе, связанном с сохранённым расчётом.

## Ограничения

- Нет подтверждённого реального сетевого объекта Магаданской области и доступа к данным. 20 кВ, 5 МВт, 2 Мвар, R=0,3 Ом и X=0,4 Ом/фаза — **условная физическая задача**, не схема Магаданэнерго.
- Перепроверка аналитического решения — независимость математического метода, **не** независимый экспертный акт электросетевой компании.
- PostgreSQL RLS есть как **не применённый** SQL blueprint. Приложение **отказывает** в PostgreSQL-режиме до реализации и тестирования доверенного tenant-контекста.
- HMAC + локальные триггеры — контроль целостности, не физически неизменяемое WORM-хранилище. Нет независимого внешнего якоря, SSO/MFA, промышленного IdP, распределённого rate limit, TLS termination, бэкапов, мониторинга, PII retention, нагрузочных тестов и промышленного допуска.
- Браузерная E2E-проверка через `http://127.0.0.1` заблокирована администратором среды тестирования и **не засчитана как PASS**. Статические CSS/HTML-макеты проверены отдельно на ширинах 1440 и 375 px.
- Никаких команд на оборудование, защиты, АСУ ТП и диспетчерские сети.

## Запуск из исходников

Требования: Python 3.11+, установленный локально Python-стек, Node.js 20+ для проверок V6; Chromium и Playwright для дополнительных UI-проверок в разрешённой среде.

```bash
cd server
python -m pip install -r requirements.txt
./run_local.sh
```

`run_local.sh` создаёт локальный файл `.lab.env` с двумя постоянными секретами (режим доступа 0600, не включён в архив). **Не менять AUDIT_SECRET без процедуры ротации**, иначе старую HMAC-цепочку нельзя будет проверить. При первом запуске `seed_lab` печатает случайные отдельные пароли тестовых аккаунтов один раз в терминал. В архиве нет действующих учётных данных. Открыть браузер в собственной разрешённой среде: `http://127.0.0.1:8000/lab`. **Не выставлять демонстрационную базу или API в публичный интернет.**

## Следующий промышленный этап

1. Корпоративный identity provider (SSO/MFA), акт разграничения ролей, утверждённая модель угроз.
2. PostgreSQL/RLS, транзакционная установка доверенного tenant-контекста и отрицательные cross-tenant тесты на реальной PostgreSQL.
3. Независимое WORM/подписанное хранение аудита, резервирование, мониторинг, восстановление, секреты в vault.
4. Протокол передачи данных выбранного магаданского объекта, допустимая сеть, паспорт измерений.
5. Сравнение с отраслевым расчётным комплексом на согласованных условиях и независимый акт инженерной приёмки.
6. Только затем проверка экономического эффекта и инвестиционное досье реального проекта.

## Нормативные и инженерные ориентиры

- [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) — least privilege, deny-by-default.
- [FastAPI OAuth2 JWT](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/) — подписанные токены, безопасное хранение паролей.
- [PostgreSQL Row-Level Security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html) — RLS, FORCE и исключения для privileged DB roles.
- [SciPy optimize root](https://docs.scipy.org/doc/scipy/reference/generated/scipy.optimize.root.html) — численное решение нелинейных уравнений.
- [NIST SP 800-92](https://csrc.nist.gov/pubs/sp/800/92/final) — организация управления журналами событий (историческое руководство; применять совместно с актуальными требованиями).
