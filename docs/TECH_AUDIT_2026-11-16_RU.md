## 2. Gap-анализ: чего нет

### 2.1 По модулям (научная часть)

**HydroForecast.** Нет: реальных рядов; метеорологических предикторов (осадки, снегозапас, температура); концептуальной гидрологической модели (снеготаяние degree-day, HBV-подобная приточность); ансамблевых прогнозов (ESP); вероятностной верификации (CRPS, reliability diagram, PIT-гистограммы по WMO-1364, который проект сам цитирует); conformal-интервалов, устойчивых к временной зависимости (проект цитирует Oliveira et al. 2024, но не реализует); горизонтов дольше 7 суток; сезонных прогнозов.

**CascadeEconomics.** Нет: маршрутизации Muskingum / Muskingum-Cunge (сейчас — чистый лаг, в документе честно признано); почасового шага (суточный усредняет пиковую работу); ледового режима — для Колымы это критично: зимние затора/зажимы меняют пропускную способность русла и отметки; оптимизации режимов (LP/динамическое программирование/SDDP) — сейчас только сценарное сравнение; экологических и водохозяйственных ограничений как формальных неравенств; модели холостых сбросов и шлюзования.

**TurbineReliability.** Модуля нет вообще (зрелость 0): ни измерительной модели, ни ISO 10816/20816 вибрационных зон, ни Weibull/survival-анализа, ни связи с CMMS/журналом ремонтов, ни калибровки P(failure). Это заявленный продукт из шести, фактически отсутствующий.

**GridLoss Planner.** Нет: многоузлового Newton-Raphson; трансформаторов/РПН, шунтов, несимметрии фаз; N−1; сверки с внешним решателем. Учебная двухузловая модель верна математически, но не масштабируется на реальную топологию. Отсутствует бенчмарк на эталонных сетях (IEEE 33-bus и т.п.).

**HeatNet Economics.** Нет: гидравлического расчёта сети (потери давления по участкам, итерационный солвер), температурного падения вдоль трубы, поучастковых теплопотерь, погодной нормализации (градусо-сутки). Сейчас — только балансовое тождество.

**HydroCAPEX.** Нет: вероятностной экономики (Monte Carlo по коррелированным факторам, tornado-чувствительность — есть только детерминированная sensitivity V77); российской налогово-тарифной модели (Магаданская энергосистема изолирована — нет ОРЭМ: регулируемые тарифы РЭК, северная компенсация; в документации это не проработано); реальных опционов (поэтапность, отложенное решение); риск-модели строительства в условиях вечной мерзлоты и северного завоза; полного IPMVP Option C (change-point модели ASHRAE, не только линейная PRE-модель).

### 2.2 Сквозные инженерные пробелы

1. **Монолиты:** `main.py` ~43 КБ, `storage.py` ~32 КБ — точки концентрации риска; каждая версия добавляет `install_*_routes` в общий файл.
2. **Фоссилизированные тесты:** `tests_v71…v810` накапливаются (16 наборов) вместо одной развивающейся системы; старое поведение консервируется, а не пересматривается. Это дорого и маскирует регрессии совместимости.
3. **Нет упаковки:** нет `pyproject.toml`/пакета, нет Dockerfile, нет lock-файла зависимостей (`requirements.txt` без пинов версий — проверить), нет `.editorconfig`/ruff/mypy-конфигурации, нет pre-commit.
4. **Нет релизов:** ни одного git-тега и GitHub Release; версии существуют только в именах веток и README. SemVer объявлен в #19, но не внедрён.
5. **Нет LICENSE** — при публичном репозитории это юридический вакуум (по умолчанию «все права защищены», что блокирует даже цитирование кода рецензентами).
6. **Документация без карты:** ~100 файлов `docs/`, 16 версионных README в корне, дублирование (ROADMAP_V8 vs V8_EXECUTION_ROADMAP_RU и др.); нет единой точки входа, нет языковой политики (RU/EN смешаны).
7. **CI-покрытие неполное:** нет публикации coverage, нет mutation/профилирования; `v89-source-quarantine` и integrity-гейт падают (#21).
8. **Данные без версионирования:** артефакты лежат в git; для будущих реальных рядов нужен DVC/аналог + внешнее хранилище (git не для гигабайтных рядов).
9. **Нет OpenAPI-агрегации:** 11 снимков openapi_v7…v83 накоплены, но нет единой актуальной спецификации с разметкой deprecated-эндпоинтов.
10. **Нет CITATION.cff / DOI** — результаты (напр. V8.10) нельзя корректно цитировать.

## 3. Программа развития: что добавить, углубить, усилить

Приоритеты: **P0** — разблокирует научную ценность; **P1** — инженерная надёжность; **P2** — развитие.

### P0-1. Реальные данные без чьих-либо разрешений (главный научный рычаг)

Ключевое наблюдение аудита: проект ждёт данных РусГидро/владельцев, но **первый честный backtest возможен уже сейчас на полностью открытых данных**:

| Данные | Источник | Доступ | Что разблокирует |
|---|---|---|---|
| Суточный/месячный сток Колымы | GRDC (Koblenz) | Бесплатно для исследований, регистрация | Реальный backtest HydroForecast |
| Метеорология бассейна (осадки, t°, снег) | ERA5-Land (Copernicus CDS) | Открыто, API | Предикторы и degree-day снеготаяние |
| Спутниковые осадки | GPM IMERG (NASA) | Открыто | Независимая проверка осадков |
| Месячный сток (контроль) | R-ArcticNET | Открыто | Водный баланс CascadeEconomics |
| Официальные ряды РФ | АИС ГМВО Росгидромета | Запрос в ведомство | Юридически чистый канал |

Программа P0-1: (a) заявка GRDC на створы Колымы (Усть-Среднекан/Среднеколымск/Колымск); (2) скачать ERA5-Land по бассейну; (3) зафиксировать источники по стандарту #18 (SHA-256, as-of, права); (4) rolling-origin backtest persistence/MA3/MA7 **на реальном ряде** — baseline; (5) добавить HBV-подобную концептуальную модель с degree-day снеготаянием и показать, выигрывает ли она у benchmark'ов (проект сам установил этот критерий в V8.2). Результат — первый внешне воспроизводимый научный результат проекта.

### P0-2. Вероятностная верификация прогноза по WMO-1364

CRPS для ансамблей, reliability diagram, PIT-гистограмма, event-based scoring для половодья; conformal с поправкой на временную зависимость (реализовать подход из цитируемой Oliveira et al. 2024) вместо rank-полосы. Это переводит HydroForecast с «честных диагностик» на публикуемую методику.

### P0-3. Маршрутизация Muskingum-Cunge в CascadeEconomics

Заменить/дополнить чистый лаг моделью Muskingum (параметры K, X) с валидацией на исторических паводках (когда появятся ряды), оставив лаг как degenerate case. Плюс почасовой шаг для оценки пиковой работы и ледовый коэффициент пропускной способности зимой (для Колымы — обязательная физика, без неё зимний водный баланс неверен).

### P1-4. TurbineReliability: от контракта к минимальному ядру

`turbine_reliability_v9.py`: измерение аномалий по вибрации/температуре с зонами ISO 20816, нормализация по режиму, Weibull-оценка времени до отказа на синтетике, экономика `E[C]` с явным флагом «P(failure) не калибрована». Закрывает заявленный, но пустой продукт.

### P1-5. GridLoss: многоузловой солвер + внешний бенчмарк

Newton-Raphson для радиальной сети N узлов; валидация против pandapower на IEEE 33-bus (открытый эталон — бесплатный независимый «решатель» и сразу зрелость 3); затем N−1 перебор. Это самый дешёвый путь к уровню BENCHMARKED среди всех модулей.

### P1-6. Инженерная гигиена (гейт D из #19)

`pyproject.toml` + пины зависимостей; ruff+mypy в CI; декомпозиция `main.py`/`storage.py` по доменам; слияние `tests_v*` в единую `tests/` с маркерами версий; SemVer-теги (`v8.11.0` на текущий main) и первый GitHub Release; Dockerfile; CITATION.cff (добавлено этим PR); единый OpenAPI; LICENSE (решение владельца); docs-сайт (MkDocs) при росте аудитории.

### P1-7. Вероятностная экономика HydroCAPEX

Monte Carlo NPV с коррелированными факторами (цена, сроки, водность), tornado-диаграммы, отдельная тарифная модель изолированной энергосистемы (регулируемый тариф РЭК, северные компенсации — исследовать действующие документы), real options для поэтапного строительства. Обязательный блок: геокриологические и логистические риски Севера как отдельные факторы CAPEX.

### P2-8. HeatNet: поучастковая теплогидравлика

Итерационный солвер давлений/расходов (аналог Hardy-Cross/Newton для теплосети), температурное падение вдоль трубы, погодная нормализация HDD, матрица «до/после» по IPMVP Option C.

### P2-9. Оптимизация каскада

После P0-3: LP/DP-диспетчеризация недели с жёсткими ограничениями (правила водопользования как неравенства), SDDP как перспектива для стохастической приточности. Только после реальных кривых и правил — иначе оптимизация синтетики не имеет смысла.

### P2-10. Научная публикация

Два результата уже сейчас имеют публикационный формат (workshop/позиционная статья): (1) V8.10 — неидентифицируемость почасовой обеспеченности из месячных агрегатов со строгим контрпримером; (2) архитектура fail-closed evidence/Boundary Graph против двойного учёта эффектов. DOI через Zenodo после первого Release.
