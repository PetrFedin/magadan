# HYDROKONTUR 360 — V8.9 строгая сверка новых потребителей с baseline

**Режим:** исключительно синтетический контроль связывания записей. Нет разрешённых исходных рядов, подписанных сведений о включении в СиПР, сетевых схем и утверждённого N−1. **PRODUCTION, BUSINESS CASE, REAL NODE CAPACITY: HOLD.**

## Что изменилось после первой версии V8.9

Раньше одна лишь текстовая ссылка `baseline_reconciliation_ref` считалась достаточной для классификации `IN_BASELINE` или `ADDITIONAL`. В реальной модели это риск: проект может оказаться включён в официальный прогноз частично, целиком или под другим договором. Новый `baseline_reconcile_v89.py` не доверяет текстовому утверждению: синтетические заявления сверяются с **отдельным реестром** версионированных строк прогноза по следующим ключам:

- `forecast_revision` — конкретная ревизия прогноза, строго `SYNTHETIC-...`.
- `canonical_consumer_id` — канонический идентификатор потребителя.
- `connection_contract_id` — договор технологического присоединения.
- `supply_point_id` — независимая точка поставки/подключения.
- `node_id` — узел подключения, только синтетический.
- `already_counted_mw` — декларируемая в синтетической записи мощность, уже учтённая в baseline.
- `evidence_ref` — **синтетический** идентификатор записи, не доказательство действительного права или оригинального файла.

Ни одна модель не получает реальных данных без разрешения. Поля `source_owner_permission_independently_verified` и `independent_engineer_approved` **принудительно FALSE** в схеме входа; пользователь не может выдать себе утверждение.

## Математика антидвойного учёта

Для одного согласованного договора:

`additional_mw = requested_mw − already_counted_mw`

Только при выполнении **всех** условий: договор уникален, строка прогноза однозначна, организация/канонический потребитель, точка и узел совпадают, прогноз одной редакции, `0 ≤ already_counted_mw ≤ requested_mw` и статус корректен:

- `IN_BASELINE` — только когда `already_counted_mw = requested_mw`, добавляется 0 МВт.
- `ADDITIONAL` — только когда `already_counted_mw = 0`, добавляется запрошенная мощность.
- `PARTIAL` — только когда `0 < already_counted_mw < requested_mw`, добавляется разность.
- `UNKNOWN` — HOLD без числового результата.

Пример, **все числа вымышлены**: проект 50 МВт, из них 30 МВт учтены в синтетическом baseline, дополнительная мощность модели — 20 МВт. Это не 20 МВт фактически доступной мощности: `actual_available_capacity_mw=null` и `approved_investment_decision=HOLD`.

Если один потребитель обслуживается несколькими разными точками, требуются разные `supply_point_id` и общая ссылка `split_allocation_ref`, иначе все суммы блокируются. Дубли одного физического пункта запрещены даже при указанной ссылке. Этот приём лишь ограничивает ошибки синтетического реестра и **не подтверждает реальное распределение нагрузки**.

## Исходный код, API и доказательства

- `server/hydro_api/baseline_reconcile_v89.py` — чистая типизированная функция `assess_baseline_reconciliation`, проверка версий и идентичности.
- `server/hydro_api/baseline_reconciliation_api_v89.py` — HTTP `POST /v89/orgs/{org_id}/baseline/reconcile`; RBAC `engineer/auditor`; чужой org — 404; детерминированные SHA-256. Никаких записей в DB/financial ledger.
- `GET /v89/meta/baseline-reconciliation-readiness` — все неподтверждённые реальные пункты указаны FALSE.
- `server/tests_v89/test_baseline_reconcile_v89.py`, `server/tests_v89/test_baseline_reconciliation_api_v89.py` — 26 параметризованных тест-кейсов.
- CI `.github/workflows/v89-source-quarantine.yml` требует **49 PASS** на точном SHA (23 прежних + 26 новых), JUnit без пропусков.
- Основная `.github/workflows/v84-full-regression.yml` теперь включает V8.9: ожидает минимум **453** Python PASS (404 прежних + 49 V8.9) при неизменных исторических допусках к известным skips старых сценариев.

В независимом контейнере выполнены `26/26 PASS` по новому чистому модулю и его изолированному FastAPI-адаптеру, Python 3.13 + Pydantic 2.x; это **не** серверный GitHub CI, не полный монолит V8.9 и не PostgreSQL17/Chromium-приёмка. На момент разработки Mac offline и GitHub runners не исполнялись на последнем ранее наблюдаемом SHA.

1. Получить правовое основание и оригинальные ряды владельцев, сверить реальный `SHA256` исходного файла в защищённой среде.

3. Независимо проверить по сетевой модели N−1, разрешённую мощность конкретных узлов, связь нагрузки/энергии, зимний максимум и маловодные сценарии.
4. Обеспечить в защищённом staging корпоративный OIDC/MFA, PostgreSQL 17/RLS и WORM-аудит; повторить UI/E2E на одном SHA и убрать инфраструктурный блокер GitHub CI.
5. Лишь после подписанных технического и экономического заключений рассматривать промышленную интеграцию. Действующее `main` и production не изменять.

**Итог:** новый алгоритм исключает самовольное присвоение проекту статуса «не учтён в прогнозе», но независимая верификация фактического регионального баланса Магаданской области всё ещё НЕ выполнена.
