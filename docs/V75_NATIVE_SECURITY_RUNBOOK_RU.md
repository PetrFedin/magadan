# ГИДРОКОНТУР 360 — МАГАДАН V7.5: безопасная нативная приёмка PostgreSQL и идентификации

**Статус:** инструкции для исполнителя. Сам факт наличия этой инструкции не означает, что проверка завершена. На момент V7.5 в рабочей среде не установлен PostgreSQL 17, поэтому **нативные миграции 001–090 и RLS-тесты не исполнены**. Не использовать производственную базу для пробного запуска.

## 1. Минимальный безопасный стенд

Выделенный новый PostgreSQL 17 (локальная машина/изолированный CI), отдельная пустая база с уникальным именем `hydrokontur_v75_native_test`, отдельные роли `hk_owner NOLOGIN`, `hk_app`, `hk_authenticator`, `hk_exporter`, `hk_migrator`, доступ только с localhost или контролируемого хоста. Пароли и ключи создаются отдельно и не хранятся в репозитории. Никаких реальных данных РусГидро и Магаданской области.

Для SQL SECURITY DEFINER: минимальные привилегии, фиксированный и безопасный `search_path`, запрет `PUBLIC EXECUTE` при отсутствии явного основания. Для таблиц с RLS: `ENABLE ROW LEVEL SECURITY`, `FORCE ROW LEVEL SECURITY`; приложение не подключается как владелец таблиц, суперпользователь или роль `BYPASSRLS`.

**Рекомендуемые официальные источники:** https://www.postgresql.org/docs/17/ddl-rowsecurity.html ; https://www.postgresql.org/docs/17/sql-createfunction.html

## 2. Установка миграций и состояние схемы

1. Создать новый кластер/контейнер PostgreSQL 17, удостовериться в версии `SELECT current_setting('server_version_num')` (должна относиться к 17.x).
2. Создать пустую тестовую базу и убедиться, что **в ней нет пользовательских таблиц**, заданных миграцией. На существующую production-базу запуск запрещён.
3. Передать `HYDRO_NATIVE_TESTS_REQUIRED=1` и тестовые `DATABASE_URL` и отдельные креденшиалы только через секреты среды.
4. Исполнить миграции `001`...`090` в порядке версий при помощи предусмотренного в репозитории bootstrap-скрипта. Любая ошибка — fail, без ручного «добивания» отдельных операторов без пересмотра миграций.
5. Проверить каталоги `pg_policies`, `pg_class.relrowsecurity`, `pg_class.relforcerowsecurity`, `pg_roles.rolbypassrls`; проверить разрешения таблиц и функций.
6. Выполнить весь набор `server/tests_v71/test_postgres_native.py`, включая V7.5-проверки; сохранить stdout/stderr, версию СУБД, суммы SQL, идентификатор запуска, результаты и список отказов.
7. Выполнить конкурентные операции в двух подключениях и rollback: собственные/чужие организации, перевыпуск полномочий, удаление членства, одновременное редактирование, replay, аудит, очередь отправки, логистические и финансовые данные.
8. Создать резервную копию лабораторной базы; восстановить на **вторую изолированную** базу; повторить проверки доступа и целостности после восстановления.
9. Подписать протокол приёмки только после независимого review SQL, удаления сервисных секретов из журналов и воспроизведения негативных тестов.

## 3. Критическая матрица отказов

| Проверка | Ожидаемый результат |
|---|---|
| Подключение без org/session | 0 чужих строк, отказ на запись |
| `SET org_id = чужой UUID` без подписанного контекста | Отказ/0 строк; не эскалирует роль |
| Org A пытается читать asset B | 404/0 строк независимо от знания UUID |
| Разные организации и совпадающие локальные коды | Нет смешивания объектов и экономических эффектов |
| Истёкшая/отозванная сессия | Немедленный отказ по политике |
| Попытка `UPDATE/DELETE` исследования | Отказ, аудит только добавлением |
| Связь HydroForecast A и Cascade B с разными org/asset | Отказ FOREIGN KEY/триггера |
| Двойной handoff для одной пары и типа | Конфликт UNIQUE, а не два независимых результата |
| Подмена SHA модели после расчёта | Replay отклонён, исходная запись не переписана |
| Смена орг. роли при открытой транзакции | Чужие записи не становятся видимыми |
| Злоупотребление `SECURITY DEFINER`/`search_path` | Нет произвольного выполнения от владельца схемы |
| Пул соединений повторно использует сессию | Контекст прошлого пользователя не переносится |
| Конкурентное согласование/финансирование | Нет двойного утверждения или двойного списания |
| Нарушение RLS после restore | Тест блокирует релиз |

## 4. Идентификация и внешний аудит

При подключении реального корпоративного IdP: проверить OIDC issuer, JWKS, аудиторию, nonce, state, PKCE, MFA/`acr`, локальные полномочия и отзыв сессий. Синтетическая IdP из предыдущей лаборатории не равнозначна корпоративному подключению. Разделять приложение, базу и администратора Identity Provider; хранить журнал входов и изменения ролей.

Аудит: приложение записывает событие атомарно с изменением/очередью, отдельный процесс доставляет, независимое хранилище выдаёт подписанную квитанцию, последующая проверка фиксирует состояние сохранения. Файловый `LAB_FILE` — **не неизменяемый архив**. Реальная WORM-приёмка включает версионирование, Object Lock/аналог, юридический срок удержания, процедуру восстановления, защиту ключей и сбои хранилища.

## 5. Browser↔API и электросетевой полевой пилот

Браузерная приёмка не считается исполненной, пока нет подтверждённого прогона: login/logout, запрет чужой организации, согласование документов, ручной replay, ошибки сети, refresh/закладки, responsive 375/768/1440 и журнал всех отказов. Ранее Chromium локально блокировал HTTP тестовой среды; нельзя выдавать статический скриншот за E2E PASS.

Для сети Магаданской области требуются письменное право на данные, актуальная однолинейная схема, измерительные ряды, паспортные параметры, базовая модель и независимый отраслевой расчёт, согласованные пороги невязки и экспертный протокол. До этого любые цифры имеют статус `SYNTHETIC_LAB_ONLY`.

## 6. Формальный критерий GREEN

`POSTGRES_RLS_NATIVE_PASS && CONCURRENCY_PASS && RECOVERY_PASS && OIDC_MFA_REAL_PASS && WORM_ACK_PASS && BROWSER_E2E_PASS && FIELD_RIGHTS_PASS && INDEPENDENT_ENGINEERING_PASS`.

При отсутствии любой составляющей `PRODUCTION_HOLD = TRUE`. Нельзя заменять пропущенный тест условной галочкой или количеством прочих тестов.
