# V7.6 · Безопасность, PostgreSQL 17 и обязательная нативная приёмка

**Статус SQL 100:** `DESIGNED_NOT_NATIVE_TESTED`. Наличие синтаксического/статического теста не означает ни успешного применения миграции, ни защищённости в действующей базе.

## 1. Критическая структура

Таблица `assurance_packs_v76`: `id`, `org_id`, `programme_id`, `reference_code`, `benefit_key`, `source_bundle_sha256`, `input_payload`, контрольные суммы, неизменяемый `snapshot`, `created_by`, `created_at`. Две уникальности против двойного учёта: `(org_id,benefit_key)` и `(org_id,programme_id,source_bundle_sha256)`. Связь `(org_id,programme_id)` — составной внешний ключ на `research_programmes`.

## 2. Контроль PostgreSQL RLS

Скрипт 100 включает `ENABLE/FORCE ROW LEVEL SECURITY`. `hk_app` может SELECT, если проверен серверный контекст организации, и INSERT только для экономиста (`hk_security.allowed`). Не предоставляет UPDATE/DELETE или TRUNCATE. Триггер при INSERT проверяет соответствие пакета программе, наличие утверждённой исследовательской WBS, принадлежность исходных handoffs той же программе и отсутствие промышленного флага. Обязателен тест на сеанс без контекста, подмену tenant, попытку авторизации по вручную заданной `GUC`, конкурентный insert и попытку изменения после отзыва полномочий.

## 3. Нативный путь допуска

1. Запустить **новый пустой выделенный PostgreSQL 17**. Скрипт bootstrap требует имя с префиксом `hydrokontur_v72_` и отказывается от непустой БД; имя сохранено из предыдущих выпусков для совместимости с проверками. Не запускать на корпоративной базе.
2. Установить зависимости `server/requirements-v71.txt`. Создать временные учётные данные исключительно для тестовой среды, не публиковать секреты в репозиторий.
3. Выполнить миграции `001..100` строго по порядку и проверить транзакционное применение (не допускать частично внесённых миграций).
4. Запустить **обязательные** `HYDRO_NATIVE_TESTS_REQUIRED=1 HYDRO_NATIVE_CONFIG=/tmp/hk-native-v76.json PYTHONPATH=server pytest -q server/tests_v71/test_postgres_native.py`.
5. Проверить не менее двух одновременных транзакций с конкурирующими заявками, повторное использование соединений, отзыв идентификации и ограничения владельца/суперпользователя.
6. Проверить backup/restore на второй новой базе, целостность аудита и невозможность штатного изменения сохранённых заявок.
7. Отдельно проверить корпоративный IdP/MFA и приёмник аудита в разрешённом внешнем хранилище; лабораторная SQLite и локальное файловое хранилище не годятся в качестве промышленного доказательства.

**Текущий результат:** PostgreSQL в данной вычислительной среде отсутствует; тесты нативной БД имеют статус `NATIVE_ACCEPTANCE_BLOCKED`. Нельзя заменять их SQLite-тестами.

## 4. Аудит и угрозы

Угрозы: cross-tenant IDOR, горизонтальная и вертикальная эскалация прав, удаление или подмена расчётного пакета, дублирование эффекта, использование старой версии модели, подмена источника, конкурентные конфликты, переиспользование сессии, конфликт бумажного и цифрового согласования. Контрмеры: per-request membership, RLS, составные FK, append-only, контроль хеша источников, уникальность бизнес-ключа и набора исходников, архив аудита. Для реальной продукции требуется независимое тестирование, включая возможность обхода защиты на уровне администратора БД/хостинга.

## 5. Восстановление

Необходимо протестировать аварийное восстановление PostgreSQL и отдельного архива из резервных копий, проверку целостности квитанций и происхождения исходных моделей. Нельзя объявлять RTO/RPO без отдельного проектного расчёта и испытаний. В V7.6 эти испытания **не выполнены**.

## 6. Правовое ограничение

Реальные данные объектов энергетики могут подпадать под требования режима информации, охраны объектов и критической информационной инфраструктуры. Юридический статус системы, применимость № 187-ФЗ, отраслевых актов, договоров и локальных регламентов определяются отдельно. Исследовательский код не получает полномочий для технологического управления.
