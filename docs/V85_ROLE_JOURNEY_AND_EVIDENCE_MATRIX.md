# ГИДРОКОНТУР 360 — МАГАДАН · V8.5 Role Journey (только лаборатория)

**Область:** независимые HTTP-сессии нескольких пользователей в изолированном синтетическом тестовом окружении. **Ниже описаны автоматизированные тесты, а не подтверждённая приёмка.** PostgreSQL17/RLS, реальные браузеры и промышленная эксплуатация остаются HOLD.

## 1. Последовательность и авторизованные пользователи

Точка входа: `server/conftest.py`, тестовые данные для `magadan-lab` и отдельно `separate-org`. Самостоятельные клиенты `TestClient` получают **разные Bearer-токены** для engineer, auditor, economist, viewer, manager и инженера другой организации. Неавторизованный клиент не получает токен.

1. Инженер запрашивает `POST /v82/orgs/magadan-lab/hydroforecast/evaluate`. Ответ содержит единственный прогнозный целевой день, временные метки, метод, предупреждения и хеши, но не сохраняет финансовый результат.
2. Инженер использует те же искусственные входные данные в `POST /v83/orgs/magadan-lab/cascade/forecast-screen`. Допустимы только две `LAB_REFERENCE` записи одной организации. Результат содержит dry/central/wet и проверяемые времена/расходы; это *сценарии*, не доказанные вероятностные квантили.
3. Аудитор в отдельной авторизованной сессии воспроизводит расчёт. JSON результатов и SHA-256 доказательств должны совпасть.
4. Экономист, руководитель и наблюдатель получают `403` при попытке выполнить инженерный расчёт; анонимный клиент — `401`. Иная организация и межорганизационный объект возвращают `404`, чтобы не раскрывать наличие чужой сущности.
5. Проверяется сохранность счётчиков `StudyRun` и `BenefitReservationV79`: read-only HTTP-модель не должна создавать исследований, финансовых заявок, команд сброса или подтверждённой экономии.
6. Отзыв membership инженера должен немедленно прекращать доступ его старой сессии (`404`), оставляя другой аккаунт работоспособным. Изменение `token_version` аудитора делает старый Bearer-токен недействительным (`401`).
7. При искусственном превышении номинальной мощности любая ветвь должна содержать `ELECTRICAL_RATED_CAPACITY_EXCEEDED`, `energy_mwh=null`, `eligible_for_financial_ledger=false`, `monetary_benefit_rub=null`, `recommended_dispatch_cms=null`. Попытка передать неприемлемый идентификатор реального SCADA-источника возвращает `422`.

## 3. Как получить настоящий тестовый результат

На одном зафиксированном SHA (чистое окружение Python 3.13):

```bash
python -m pip install -r server/requirements.txt
PYTHONPATH=server python -m pytest -q -ra -o xfail_strict=true \
  server/tests_v82 server/tests_v83 server/tests_v85 \
  --junitxml=/tmp/magadan-v85-junit.xml
python scripts/v84_junit_gate.py --junit /tmp/magadan-v85-junit.xml \
  --shard v85-role-journey --min-passed 3 --max-skipped 0 \
  --actual-sha "$(git rev-parse HEAD)" --expected-sha "$(git rev-parse HEAD)" \
  --require-case test_independent_role_sessions_forecast_to_cascade_without_financial_post \
  --require-case test_revocation_invalidates_existing_sessions_without_harming_other_role \
  --require-case test_peak_violation_cannot_enter_money_or_dispatch_in_any_role
```

Команда с одинаковым `actual-sha`/`expected-sha` — только локальная отладка. **Доказательством для релиза** считается исполнение того же файла на строго заданном SHA PR, подтверждённое внешним успешным runner, Job Summary и независимо проверенными тестовыми логами. JUnit `skip` и `xfail` не могут маскировать обязательный тест; `XPASS` запускается со строгим правилом отказа.
