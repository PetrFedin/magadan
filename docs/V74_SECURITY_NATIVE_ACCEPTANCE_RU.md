# V7.4 — безопасность, полномочия и нативная приёмка PostgreSQL

**Статус: проектная защита реализована в SQLite/HTTP лаборатории; RLS PostgreSQL 17 не проверена на настоящем сервере. Официальный промышленный допуск отсутствует.**

## 1. Контуры аутентификации

Лабораторный пароль / JWT и тестовый OIDC-адаптер не дают права использования корпоративных данных. Подключение реального корпоративного IdP потребует отдельного разрешения, OIDC-конфигурации, MFA, разрешённых redirect URI, политики сроков сессии, отзывов прав и аудита. Из токена IdP не должны автоматически переноситься произвольные корпоративные роли; права устанавливаются в серверном реестре членства.

## 2. PostgreSQL 17, SQL миграция 080

Порядок применения: `001_schema.sql`, `010_identity_and_context.sql`, `020_rls_and_links.sql`, `030_audit_and_workflow.sql`, `040_seal_policy.sql`, `050_receipt_authenticity.sql`, `060_studies_v72.sql`, `070_grid_economic_dossiers_v73.sql`, `080_research_programme_v74.sql`. Скрипт `scripts/bootstrap_native.py` требует **новую полностью пустую базу** с именем `hydrokontur_v72_*`, в противном случае отказывается работать. Не запускать в общем, рабочем, корпоративном либо продакшен-кластере.

На таблицах `research_programmes`, `research_programme_studies`, `research_programme_finance`, `research_programme_links` заявлены `ENABLE ROW LEVEL SECURITY` и `FORCE ROW LEVEL SECURITY`, роль `hk_app` без владельца/BYPASSRLS, `SELECT` по `hk_security.allowed(org_id)`, `INSERT` для роли economist, проверка `created_by` по текущему actor для головной записи, составные FK `(org_id,id)`, запрет UPDATE/DELETE и события аудита.

Trigger `validate_research_link()` предназначен для запрета направления связи против правила шести модулей и несовпадения группы сценариев. Trigger `validate_research_finance()` предназначен для отказа финансовому мемо, чьи базовая и альтернативная модели не прикреплены к тому же пакету. Эти механизмы нельзя считать фактически работающими до нативного испытания.

## 3. Обязательные негативные испытания PG

| Сценарий | Ожидаемое поведение |
|---|---|
| Сессия отсутствует | `SELECT` ничего не показывает, `INSERT` запрещён |
| Подмена `org_id`/session GUC | запрещён доступ к данным иной организации |
| Попытка `SET ROLE hk_owner` | отказ для прикладной роли |
| Инженер или viewer создаёт программу | запрет по роли |
| Экономист подставляет другого `created_by` | отклонение политикой |
| Дочерняя запись с чужим `org_id` | отказ составного FK / RLS |
| Финансовый мемо без пары источников в пакете | отказ trigger `validate_research_finance` |
| Некорректное направление HydroForecast→HeatNet | отказ trigger `validate_research_link` |
| Изменение или удаление сохранённого досье | отказ append-only trigger |
| Удаление членства при живой сессии | последующая операция отклонена |
| Повторное использование пулового соединения | контекст прежнего пользователя не утёк |
| Одновременные создания с одинаковым reference_code | одна успешна, остальные завершаются конфликтом |
| Частичная ошибка после вставки головной записи | все дочерние изменения и аудит откатываются |
| Неподписанная внешняя квитанция | не засчитывается как подтверждение хранения |
| Потеря данных и восстановление | RPO/RTO подтверждаются отдельным регламентом, не предполагаются |

## 4. Почему лабораторный успех не равен нативному

Тесты SQLite проверяют отношения FK, приложение и Python-ограничения, но **не** исполнение SQL-политик PostgreSQL. В текущей среде нет PostgreSQL server/psql и нет `HYDRO_NATIVE_CONFIG`. При `HYDRO_NATIVE_TESTS_REQUIRED=1` нативный тест завершается `NATIVE_ACCEPTANCE_BLOCKED`. Это правильный fail-closed результат, а не «тест пройден».

Ручной CI `.github/workflows/native-v74.yml` подготовлен локально, но не опубликован и не запускался. Используйте только после ревью прав и исходников в выделенном непроизводственном репозитории. Не создавать платный облачный ресурс без явного согласования.

## 5. Аудит и доказательства

Лабораторная HMAC-цепочка позволяет обнаружить некоторые изменения записей при сохранности отдельного ключа. Для промышленного применения необходимо подтвердить безопасность ключей, внешнее хранение квитанций, проверку retention, цепочку доверия и восстановление после отказов. В SQLite owner/admin инфраструктуры может обойти защиту через прямой доступ к файлам: **лаборатория не WORM**.

## 6. Критерии производства

`P0-HOLD` до одновременного наличия: (1) пройденная native PG17 приёмка, (2) корпоративная идентификация и MFA, (3) внешний аудит, (4) письменно согласованное право на данные магаданской площадки, (5) независимая инженерная проверка, (6) согласованная финансовая методика, (7) план эксплуатации/резервного восстановления и ИБ-заключение. Наличие семи пунктов не означает автоматического разрешения на технологическое управление, поскольку программа такого управления не предусматривает.
