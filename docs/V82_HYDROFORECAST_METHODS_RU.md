# ГИДРОКОНТУР 360 — МАГАДАН · HydroForecast V8.2

**Состояние:** лабораторная инженерная разработка. **Дата:** 1 ноября 2026 года. **Инфраструктура:** FastAPI / Python, синтетические данные. **Никаких измерений, прогнозов или денежных результатов реальных объектов Магаданской области нет.**

## 1. Предмет и границы задачи

В V7.2 `ForecastCase` принимал *уже рассчитанные* значения и оценивал исторические ошибки — MAE/RMSE/coverage. В V8.2 создан **генератор однонаправленных h-суточных прогнозов ежедневного среднего расхода Q**, воспроизводящий хронологический цикл выбора модели, калибровки диагностической полосы и независимой оценки на следующих 28 днях.

Единица: `Q`, м³/с. Серия описывает **средний расход за заканчивающиеся в `observed_at` предыдущие 86 400 секунд по времени UTC**. `available_at` — время, когда соответствующее значение было известно исследователю, **не время самой физической пробы**. Лабораторный протокол требует регулярные даты, UTC 00:00, отсутствие пропусков и доступность показаний не позднее 12 часов после отметки. Это допущения данной реализации, **не утверждённая спецификация реального гидропоста**.

Вход: не менее 112 и не более 730 **синтетических** наблюдений, один лабораторный `asset_id`, горизонт 1–7 суток и номинальное значение `1−alpha` при `alpha=0.05…0.25`.

## 2. Три простые кандидата и хронологический backtest

Для прогнозируемой даты `t` и горизонта `h` (дней) доступная история заканчивается в `i=t-h`. Горизонт `h` — **расстояние между дневными UTC-метками**, а фактическое время до целевой метки в момент выпуска равно `24h−offset_issuance`, где `offset_issuance` — число часов после последней дневной UTC-метки. Например, при `h=2`, `as_of=10:00 UTC`, фактический lead равен **38 часам**, а не полным 48 часам. Это явно возвращается как `actual_forecast_lead_hours`.

- **Persistence:** `Q_hat(t|i)=Q_i`.
- **Rolling-mean-3:** `Q_hat(t|i)=(Q_i+Q_{i-1}+Q_{i-2})/3`.
- **Rolling-mean-7:** `Q_hat(t|i)=sum(Q_{i-k}, k=0..6)/7`.

Это прозрачные **benchmark-модели**, а не калиброванная модель снеготаяния, приточности Колымского каскада или прогноз осадков. Они нужны, чтобы удостовериться, что новая статистика действительно считает прогноз и что сложная модель в будущем будет обязана выигрывать у честного простого эталона.

Для ряда из `N` значений, контрольные группы непересекаются:

| Группа | Индексы | Назначение |
|---|---|---|
| Ранняя история | `0 … N−85` | История, доступная на первых прогнозных датах |
| Выбор модели | `N−84 … N−57` | Сравнение MAE трёх моделей, **единственный** источник выбора |
| Калибровка | `N−56 … N−29` | Размер полосы абсолютной ошибки только выбранной модели |
| Holdout | `N−28 … N−1` | Финальная оценка, не используется для выбора модели и полосы |

**Rolling-origin:** при оценке каждой исторической целевой даты модель использует лишь наблюдения с `observed_at` не позднее даты выпуска `t-h`, уже доступные до выпуска. **Время выпуска для каждого исторического прогноза строго соответствует `as_of` по времени UTC-дня:** если последний запрос выполнен через 10 часов после дневной отметки, каждый исторический origin тоже использует `+10 часов`. Показания с `available_at > issued_at` отклоняются, даже если они были известны к окончанию всего исторического исследования. На более поздних датах holdout могут использоваться ранее появившиеся фактические значения из того же holdout — это **последовательная оценка с обновлением доступной информации**, а не прогноз всего 28-дневного горизонта, сделанный единожды.

## 3. Точность прогнозов и ограниченность проверки

Для `n` независимых целей оценки по календарю (не обязательно статистически независимых):

\[
MAE = n^{-1}\sum_t |\hat Q_t-Q_t|,\quad
RMSE=\sqrt{n^{-1}\sum_t (\hat Q_t-Q_t)^2},\quad
Bias=n^{-1}\sum_t (\hat Q_t-Q_t).
\]

\[
WAPE=100\frac{\sum_t |\hat Q_t-Q_t|}{\sum_t Q_t},
\quad Skill=100(1 - MAE_{model}/MAE_{persistence}).
\]

При нулевом знаменателе WAPE/Skill — `null`, не 0. При отрицательном Skill новая модель **хуже** persistence. Ошибка может быть меньше нуля при систематическом занижении — это показывается отдельно.

Для радиуса полосы абсолютной ошибки калибровки `e_i=|Q_i−\hat Q_i|`, `n_cal=28`:

\[
 k=\lceil (n_{cal}+1)(1-\alpha)\rceil,\quad r=e_{(k)},
\quad [L_t,U_t]=[\max(0,\hat Q_t-r),\hat Q_t+r].
\]

При номинальных 90%: `k=ceil(29×0.9)=27` из 28 калибровочных абсолютных ошибок. Holdout-coverage = число попавших в полосу / 28. **Это не гарантированный 90%-й предсказательный интервал**: последовательная зависимость, резкие смены гидрологического режима и экстремумы нарушают предпосылки классического exchangeability. Результат маркируется `SPLIT_ABSOLUTE_RESIDUAL_RANK_NOT_TIME_SERIES_COVERAGE_PROOF`.

Отдельные диагностические показатели: lag-1 корреляция ошибок, сдвиг bias между калибровкой и holdout, ошибка на high-flow днях по порогу p90 предыдущей истории. Если в holdout меньше пяти high-flow дней, хвостовая оценка признана недостаточно представительной. Нет p-value, нет утверждённых вероятностей превышения, нет «уверенности» в реальном прогнозе.

## 4. Сценарии и воспроизводимый эксперимент

Исходный ряд задаётся **программно**, а не считывается с гидропоста:

\[
Q_i = 160 + 0.16i +15\sin(2\pi i/32)+5\sin(2\pi i/8)+4\cos(2.1i).
\]

Для стресс-проверки последние 28 значений получают дополнительный сдвиг `+30`, `+65` или `−30 м³/с`. Все значения, даты, source_ref, определения окон, SHA и результаты можно восстановить командой:

```bash
cd <source-root>
PYTHONPATH=server python scripts/reproduce_v82.py
PYTHONPATH=server python scripts/plot_forecast_v82.py
PYTHONPATH=server python -m pytest -q server/tests_v82
```

Прогнозы относительно `as_of` исторического синтетического кейса в **2026 году**, а не «текущий прогноз на сегодня». Выбор 168 суток, 28+28+28 и сдвига +65 — **допущения экспериментальной методики**, а не сведения об объекте энергетики.

## 5. Переход к объёмам воды и экономике — важное ограничение

Суточный средний расход может быть переведён в объём **только одного целевого дня**:

\[
V_{day,\text{млн м³}} = Q_{day,\text{м³/с}}\times 86\,400/10^6.
\]

Ошибка MAE в суточных расходах аналогично пересчитывается в условную ошибку объёма *одного дня*. При горизонте 7 суток **нельзя умножать прогноз для седьмого дня на семь**: прогноз целевого дня не является интегралом расхода за всю неделю.

Значения объёма **не переходят автоматически в MWh, RUB, CAPEX, предотвращённый ущерб или инвестиционный результат**. Для этого необходимо подтвердить как минимум: преобразование гидропост → приточность конкретного водохранилища; боковой приток, задержки, ограничения по использованию воды; кривую объём–отметка–напор, КПД как функцию Q/H, график выпуска и целевой объект. Даже физически верное число MWh само по себе не даёт денежную выручку без допустимой экономической методики.

Поэтому **V8.2 не записывает прогноз в реестр выгод**, не изменяет состояние HydroCAPEX и не формирует команды гидроэлектростанциям или диспетчеру.

## 6. Что сделано в коде и как использовать

- `server/hydro_api/forecast_v82.py` — строгие исходные типы, выбор модели, калибровка, holdout, статистика, conversion Q→V.
- `server/hydro_api/forecast_api_v82.py` — stateless API `POST /v82/orgs/{org_id}/hydroforecast/evaluate`, роли `engineer` / `auditor`, tenant/asset LAB checks, SHA-256 входа/ответа/движка. Не сохраняет или не утверждает исследования.
- `GET /v82/meta/hydroforecast-readiness` — фактический лабораторный статус.
- `server/ui` — отдельная панель с исторической кривой, прогнозом, диагностической полосой и признаками риска.
- `server/tests_v82` — тесты отрицательных дат, утечки, диапазонов, изоляции, метрик и регрессии.
- `artifacts_v82` — 20 воспроизводимых сценариев, вход/выход, CSV, PNG и журнал исполнения.

Ссылки подтверждают применимость методологических понятий, **а не промышленную пригодность нашей модели**.

## 8. Минимальная следующая полевая программа

1. Соглашение о доступе к данным с владельцем конкретного гидропоста и водохозяйственных ограничений.
2. Даты, UTC/местная зона, интервалы измерений, ревизии первичных данных, качество, пропуски, time-of-availability.
3. Архив минимум нескольких водных сезонов, включая высокую/низкую воду и отдельный финальный год, не использованный при настройке. Не устанавливать длительность по одному лабораторному эксперименту.
4. Дополнительные причинные факторы: осадки, снегозапасы, температура, upstream releases, уровень водохранилищ, режимы водопользования.
5. Сравнение с гидрологическими моделями и профессиональными прогнозами; разные горизонты, влажные/сухие годы, event-based scoring, bias, reliability.
6. Независимая профессиональная проверка ошибочных предупреждений, эффекта изменения режима и безопасных порогов.
7. Согласованная гидроэкономическая методика и обязательная верификация до инвестрешения.

**Итог:** V8.2 реализует измеримый лабораторный шаг в аналитике; все практические заключения для Магаданской области остаются на `FIELD DATA / INDEPENDENT HYDROLOGY / PRODUCTION HOLD`.
