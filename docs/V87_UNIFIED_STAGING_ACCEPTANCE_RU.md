# HYDROKONTUR 360 — V8.7: единая защищённая SYNTHETIC staging-лаборатория

> **Ключевая граница:** защищённое *лабораторное* интеграционное окружение ≠ корпоративный staging. Здесь реальный PostgreSQL17, PKCE/OIDC, браузерные роли, аудит и восстановление проверяются совместно, но IdP синтетический, настоящую MFA-церемонию он НЕ проводит, корпоративная инфраструктура, внешний WORM и реальные данные НЕ подключены. Production HOLD.

## Что изменено относительно V8.6

1. Добавлен `server/tests_v87/test_pg_oidc_browser_unified_v87.py`: одна реальная PostgreSQL17 БД с FORCE RLS, отдельные роли hk_app и hk_authenticator, HTTP OIDC authorization code + PKCE, серверные cookie/CSRF/отзыв, настоящий Chromium для engineer/auditor/economist/manager/viewer/other-tenant, аудиторская цепочка и запреты доступа. Синтетический IdP имеет только тестовый ACR, в том числе отрицательные сценарии: слабый ACR и неизвестный subject.
2. Объект создаётся через настоящий защищённый API инженера; прямой административный INSERT без audit context закономерно отклоняется.
3. `scripts/v87_backup_restore.py`: реальный pg_dump/pg_restore через PostgreSQL17 клиент; новый случайно именованный пустой restore target на loopback; сверка 35 таблиц, строк, 86 политик RLS, 60 триггеров, проверка default DENY от hk_app без сессии. После проверки удаляется только собственная временная восстановленная база; исходная БД не удаляется.
4. Одна разрешённая PostgreSQL17-normalization: в pg_get_expr правило initiative_evidence получает семантически эквивалентную перестановку приведения `ARRAY[varchar]::text[]` ↔ `ARRAY[varchar::text]`. Оба точных выражения нормализуются, любые другие отличия схемы, содержимого, политик, триггеров приводят к FAIL.
5. `.github/workflows/v87-unified-staging.yml`: реальный Linux postgres:17, Playwright Chromium, 2 unified OIDC/PG/browser теста, затем 40 native PG17 RLS тестов **на той же базе**, затем восстановление и fail-closed JUnit gate с контрольными суммами на одном Git SHA. В GitHub Actions нет публичного staging URL и нет корпоративных секретов.

* Нативная PostgreSQL17 регрессия **40 PASS, 0 skip** на той же базе уже после браузерного тестирования.
* Реальный dump → отдельный restore: **35 таблиц, 86 RLS политик, 60 триггеров, 2 200 строк**, равенство по каждой таблице и сохранение default deny подтверждены. Число строк соответствует конкретной синтетической лаборатории, а не фактическим данным ГЭС.
* Эти предварительные прогоны выполнены ДО фиксации итогового SHA, следовательно GREEN GitHub workflow должен быть подтверждён отдельно.

## Локальный replay на точном SHA

После фиксации исходников, на новой изолированной PostgreSQL 17 БД и с установленным Chromium:

    export HYDRO_NATIVE_CONFIG="$PWD/runtime/qa-v87/native-config.json"
    export HYDRO_BROWSER_EXECUTABLE="<локальный абсолютный путь к Chromium>"
    bash scripts/run_v87_local_acceptance.sh "$(git rev-parse HEAD)"

Runner отказывается работать на незакоммиченном дереве или неверном SHA. Он выполняет 2 интеграционных HTTP/Chromium теста, затем 40 нативных PostgreSQL17 тестов в **той же** базе и реальный backup/restore. Контрольная квитанция: ignored runtime/qa-v87-FULL_SHA/acceptance-receipt.json. Это лабораторная, а не корпоративная авторизация.

## Файлы с доказательствами

Результаты на Mac только в ignored `runtime/qa-v87/` (секреты и скриншоты не коммитить). В GitHub Actions выводится SHA JUnit и SHA receipt, но не содержимое секретов. Ни один прогон не использует внешнюю энергосеть, SCADA либо расчёты для распоряжений.

## Обязательные этапы корпоративного STAGING (не пройдены)

| Контроль | Что именно должно быть независимо подтверждено |
| --- | --- |
| Изолированная защищённая площадка | Выделенное staging-окружение, собственная БД, HTTPS с доверенными сертификатами, закрытый доступ/VPN/Zero Trust, отдельные тестовые организации, deny-public, резервные копии и журнал изменений инфраструктуры |
| Настоящий OIDC/MFA | Реальный корпоративный IdP, зарегистрированный confidential client, exact HTTPS redirect URI, реальный сотрудник с MFA/Passkey, независимо подтверждённые acr/amr, revoke, session binding, CSRF, провал без MFA; отсутствие Bearer laboratory fallback |
| Единые проверки | Реальный Chromium после корпоративной MFA-сессии обращается к реальной PG17/RLS базе под hk_app; чужая организация недоступна, независимые сессии/потоки и отзыв корректны, рабочие маршруты и отрицательные операции проходят |
| Аудит и WORM | Подпись, экспорт и запись во внешнее WORM-хранилище, доказательство retention, права доступа, проверка replay, отделение полномочий от оператора приложения |
| Восстановление | Snapshot/PITR, восстановление в другую закрытую среду, сверка фактических данных/прав/индексов, задокументированные RPO/RTO, независимый протокол восстановления |
| Инженерная экспертиза | Только данные ГЭС с разрешением на использование, реальные кривые, независимый эталон, погрешности и чувствительность, ограничения правил эксплуатации, подписи специалистов, запрет денежных расчётов и промышленной диспетчеризации до допуска |

До поступления реквизитов разрешённого корпоративного IdP и выбора защищённой площадки **заявлять реальное корпоративное staging/MFA, независимый инженерный sign-off и production нельзя**.
