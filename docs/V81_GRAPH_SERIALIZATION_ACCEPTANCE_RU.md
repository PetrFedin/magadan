# ГИДРОКОНТУР 360 — МАГАДАН V8.1: атомарная связь физических границ и экономических эффектов

**Статус на 1 ноября 2026 года:** SQL-кандидат + локальные тесты; нативная PostgreSQL 17 не проверена. Никаких реальных измерений Магаданской области, признанных денежных выгод и допуска к промышленной эксплуатации.

## 1. Дефект конкурентной целостности V8.0

В миграции `150_boundary_graph_v8.sql` две операции использовали разные механизмы:

- Изменение графа измерительной границы проверяло `EXISTS(benefit_reservations_v79)` и отклоняло изменение после первого эффекта, но **не блокировало транзакцию с конкурентным резервированием эффекта**.
- Вставка нового `benefit_reservations_v79` брала advisory lock только для сочетания `(org_id, physical quantity class)`; обновление графа с таким ключом не синхронизировалось.

При параллельном выполнении возможен порядок: T1 проверяет, что эффекта ещё нет; T2 проверяет, что граф ещё допустим; обе вставки успешно фиксируются. Результат нарушает требование: «после первого зарегистрированного эффекта его физическая граница неизменна». Это **обоснованная потенциальная гонка**, а не доказанный случай на промышленной БД.

## 2. Исправление V8.1 — отдельная миграция 160

Вместо переписывания исторической миграции 150 добавлена `160_boundary_claim_serialization_v81.sql`. Она заменяет тела двух существующих trigger-функций, не меняет таблицы, привилегии и исторические исходники.

В обеих операциях **до чтения конкурентного состояния** берётся одинаковая транзакционная advisory блокировка:

```sql
PERFORM pg_catalog.pg_advisory_xact_lock(
  pg_catalog.hashtextextended('hk:v81:boundary-claim:org:' || NEW.org_id, 0)
);
```

Возможные сценарии при `READ COMMITTED`:

| Порядок сериализации | Результат |
|---|---|
| Регистрация эффекта первой | Изменение границы после неё должно получить отказ `BOUNDARY_GRAPH_FROZEN_AFTER_FIRST_CLAIM` |
| Изменение границы первым | Резервирование должно прочитать уже зафиксированную границу и отказать при конфликте классов, неучтённых активах или пересекающихся экономических периодах |
| Два эффекта одной организации | Операции сериализуются по организации, затем по исходному ключу количества; GIST-ограничения продолжают действовать |
| Две разные организации | Ключи блокировки отличаются; операция одной организации не должна менять границы другой |

`hashtextextended` имеет 64-битный результат: коллизия может создать **избыточную сериализацию**, но не разрешает конфликтующую запись. Все права RLS и `SECURITY DEFINER` должны дополнительно пройти проверку в реальной PostgreSQL 17.

### Зачем ограничение READ COMMITTED

Механизм опирается на то, что SQL-запрос после ожидания advisory lock увидит вновь зафиксированные строки. При `REPEATABLE READ` транзакция может сохранить прежний снимок. Поэтому до независимой проверки поведения более строгих уровней обе операции отклоняют их с ошибкой `V81_GRAPH_CLAIM_REQUIRES_READ_COMMITTED` (SQLSTATE 25000). Это консервативное инженерное ограничение, а не универсальная рекомендация по изоляции для всех бизнес-операций.

## 3. Проверки и ограничения

- `server/tests_v81/test_sql_graph_serialization_v81.py` — проверка идентичности обоих ключей, порядка операций, ограничений ролей, последовательности SQL 001–160 и **неизменности** оригинального SQL 150 по SHA-256 из исходного архива.
- `server/tests_v81/test_pg_graph_freeze_native_v81.py` — **только при выделенной PostgreSQL 17 и credentials** проверяет установленное тело функций, реально удерживаемую транзакционную advisory блокировку и отказ под `REPEATABLE READ`. Без конфигурации модуль пропускается с явной пометкой, при `HYDRO_NATIVE_TESTS_REQUIRED=1` — завершает сборку ошибкой.
- Изменены устаревшие тесты порядка миграций V7.2/V7.6/V7.7: они теперь ожидают SQL 160 как последнюю миграцию, сохраняя полный перечень и все исторические шаги.
- Никаких признанных эффектов, одобренных CAPEX или подключений к энергетическому оборудованию это изменение не добавляет.

**Обязательные следующие фактические проверки:** синхронные PostgreSQL-транзакции «изменение графа ↔ первый подтверждённый источник эффекта» и «эффект ↔ эффект», разные организации, права `hk_app`/`hk_owner`, конкурентный rollback, изоляция клиентов, независимое code-review. Эти проверки не заменяются статическими тестами.
